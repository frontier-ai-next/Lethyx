# План развития UM-MEM как адаптирующейся памяти агента

## Реализованные изменения (2026-10-22)

Обновлено 2026-10-23 после проверки межсессионного поведения и review адаптера.

- Исправлена потеря `kind` в общем упаковщике контекста. Компактный MCP сохраняет
  доступные атрибуцию, статус проверки и временные границы; они не повышают доверие.
- Явно сохранённые долговременные `user_statement` теперь доступны через recall
  в следующей сессии при `include_candidates=True` по тем же ограничениям, что
  `agent_tool_claim`. Раньше после смены run они оставались видимыми через exact
  read/recent, но исчезали из обычного поиска. Это не публикация и не директива.
- Компактная активная маска возвращает причину разрешения, scope status, ID,
  ревизию и бюджет. Отсутствие маски явно обозначается как `absent`.
- Обычные и компактные инструкции описывают использование памяти внутри задачи,
  исправление содержания и устаревшего заголовка, различие цитаты и интерпретации,
  а также ручную доставку маски в tools-only хосте.
- Навигация по workspace использует выборку ветки в SQLite snapshot: читаются
  видимые блоки и путь, ссылки на детей и связи нужных узлов. Полное чтение
  топологии и запрос связей для каждого постороннего блока удалены из этого пути.
- Добавлен отдельный адаптер `integrations/opencode` для OpenCode V2: MCP-процессы
  привязаны к host session ID; инструменты и `session.context` используют один
  scope. Маска разрешается перед первичным модельным раундом, включая продолжения
  после инструментов. Пассивная память не активируется автоматически.
- Нативный smoke Mnemosyne проверил запись, поиск с сохранённым типом, выбор
  фокуса, исправление, следующий раунд, отсутствие утечки во вторую сессию и
  деактивацию, а также явный поиск общего workspace-факта из второй сессии.
  Это проверка callbacks адаптера через настоящий MCP/native backend,
  отдельно от проверки реального интерфейса OpenCode.
- По результатам независимого review: idempotency key записи связывает session,
  message и tool-call ID; при заполнении пула вытесняются простаивающие соединения;
  ошибки MCP сохраняются как ошибки инструментов хоста. Все три сценария покрыты
  проверками транспорта.
- Живая проверка в OpenCode desktop service 2.1.2 с GPT-6 Astra и отдельной
  временной конфигурацией прошла: модель ответила `Q7M4Z` из активной памяти,
  после исправления — `N8T2L`; после подтверждённого `compaction completed` и
  ещё одного исправления — `R3Z9V`, а во второй сессии без маски — `UNKNOWN`.
  Тестовые сессии и их временное хранилище удалены. Постоянное подключение
  пользователя этим smoke не изменялось.
- Проверка загрузчиком OpenCode обнаружила, что для локального каталога нужен
  корневой entrypoint. Добавлен `integrations/opencode/index.js`, переэкспортирующий
  собранный плагин; тест использует настоящий `Host.resolve`.
- После выбора пользователя «Во всех проектах» адаптер включён в глобальной
  конфигурации OpenCode. Прежнее самостоятельное MCP-подключение заменено;
  хранилище, backend и multilingual semantic settings сохранены. Host API
  подтвердил `um-mem: active`, текущие инструменты — настоящий session ID.
- Адаптер сохраняет structured output MCP, поэтому Code Mode получает объекты,
  а не JSON-строки. Это проверено отдельной регрессионной проверкой и живым
  обновлением каталога инструментов после сборки.
- Проверки предыдущего этапа: `pytest -q` — **1497 passed, 7 skipped**; тесты адаптера
  с нативным smoke — **4 passed**; Ruff check/format, сборка Python-пакета и
  строгая сборка MkDocs прошли. Независимый review выполнен, замечания исправлены.

### Следующий этап: страницы, локальные метрики и работа агента

- `expand_block(limit=50, cursor="")` и `navigation_envelope` выдают страницы;
  курсор проверяет workspace, profile, родителя и ревизию каталога. Метакаталог
  использует собственную стабильную ревизию. Устаревший курсор требует нового
  обхода, а не тихого продолжения с пропусками.
- `block_map(child_limit=50)` ограничивает превью; глубокий workspace-обход
  материализует не более 201 описания узлов. `child_count` отражает всю ветку:
  пустое превью не означает лист и не делает ветку доступной для записи.
- Параметры и курсоры проходят через Python, MCP, компактные ответы и Hermes;
  OpenCode получает их из схем MCP.
- Раскрытие использует `block_health` только для выбранного узла и показанных
  детей. Операция читает локальные наблюдения, не проверяет сеть или готовность
  провайдера и явно возвращает `not_probed`. Счётчики записей ограничены профилем,
  события суммируются по физическому разделу через ревизии каталога. Проверяется
  соответствие физической identity её стабильному ключу до дедупликации.
- Независимый review выявил и помог закрыть ошибки метакурсора и смешивания
  счётчиков; регрессии также покрывают разделённые блоки и некорректные пары ключей.
- На настоящем хранилище обнаружено сосуществование старого static-раздела и
  текущего UUID-раздела одной ветки. Это допустимая история, а не причина отказа:
  текущие записи теперь считаются по точному физическому ключу и профилю, с учётом
  опубликованных переназначений. Проверенный пример вернул счётчики **1 и 0**,
  сохранив историю и её наблюдения.
- Отдельно исправлен split → revive: восстановленный исходный блок не считает
  записи, уже переданные новым владельцам. И описания веток, и метрики учитывают
  входящие и исходящие опубликованные переназначения, проверяя только ID выбранной
  ветки ограниченными пакетами.
- Нативный сценарий адаптера расширен: страницы → запись → исправление → смена
  фокуса → опровержение/отзыв гипотезы → новая сессия и явный поиск общей памяти.
- В настоящем OpenCode агент сам выбирал блоки и операции для PELICAN-QA:
  сохранил Python/SQLite и отдельную неподтверждённую гипотезу, исправил Python
  на Rust и статус гипотезы на refuted. После compaction и в новой сессии вернул
  Rust, SQLite и refuted. Это сценарий с явными пользовательскими уточнениями,
  а не доказательство самостоятельной рефлексии на любых задачах.
- Первый запуск QA обнаружил ошибку окружения: при уже глобально установленном
  плагине инструменты обращались к глобальному workspace, а не к тестовому.
  QA теперь использует отдельный plugin ID/namespace и проверяет workspace до
  записи. Рабочий сервис памяти перезапущен для подхвата новых параметров API.
- На основании трассы `block_map` и `recall` закреплены в каталоге Code Mode.
  В одном повторе число раундов модели изменилось: capture **7 → 6**, correction
  **6 → 5**, after_compaction **3 → 2**, fresh_session **3 → 3**. Все проверки
  фактов прошли. Это наблюдение одного сценария; общее улучшение качества или
  стоимости не установлено. Новый QA-отчёт отдельно сохраняет input/output и
  cache-read/cache-write counters; у первого запуска нет cache counters, поэтому
  сравнение общей стоимости токенов по этой паре не заявляется.
- Финальная проверка этапа: **1519 passed, 7 skipped** в Python; **4 passed**
  у адаптера с нативным Mnemosyne. Review замечаний к последней коррекции не
  оставил. Рабочий сервис обновлён; на нём проверены курсор мета-дерева и ветка
  с историческими физическими разделами. Сохранённая процедура развёртывания
  исправлена по результатам фактического сбоя со старым процессом сервиса.

На синтетической ветке из 2000 непосредственных детей первая страница вернула
50 детей вместо 2000: полный Python payload **3 483 559 → 92 357 байт**, медиана
8 локальных повторов **456.946 → 9.903 мс**. Полный обход страниц проверен на
совпадение набора и порядка со старой выдачей. Backend отключён для этого
профиля каталога; это не полная задержка MCP или модели. Артефакты находятся
в локальном Temp/opencode (`um_mem_wide_navigation_profile.json` и
`um_mem_agent_workflow_result.json`), не в release tree.

### Оставшиеся проверки и развитие

- Реальный OpenCode V2 найден отдельно от старого CLI в PATH: desktop service
  сообщает 2.1.2. Доставка в нём проверена, плагин типизирован против API
  `@opencode/plugin` 2.1.3. Постоянное глобальное подключение включено по выбору
  пользователя; явные проектные настройки хоста могут переопределять глобальные.
- Task scope адаптера равен разговору: публичный context hook даёт session ID,
  но не устойчивый идентификатор подзадачи. Смена подтемы требует смены фокуса.
- Пагинация веток и локальная диагностика реализованы. Стоимость очень большой
  истории событий внутри одного раздела и большого числа графовых связей ещё
  требует отдельного профилирования; страницы детей не ограничивают эти истории.
- Сравнительное качество воспоминаний, частота полезной рефлексии и экономия
  токенов на широкой выборке длинных модельных задач ещё не измерены. Один живой
  многошаговый сценарий выполнен; нужны одинаковые наборы задач,
  модели и бюджеты для прямого бэкенда и UM-MEM, согласно evaluation protocol.

Разделы ниже сохраняют исходные цели и результаты аудита; они не означают,
что вся программа самоадаптации уже завершена.

## Цель и границы

Цель пользователя — не только удобная записная книжка, а развивающаяся память
агента: замечать повторения в совместных обсуждениях и работе, формировать
проверяемые гипотезы о пользователе и проекте, учиться на результатах, менять
свои блоки и выбирать актуальный фокус. Агент сам предлагает, ищет, сравнивает,
исправляет и организует память; человеку не нужно вручную подтверждать каждую
обычную запись. Память остаётся вспомогательной: хост отвечает за разрешения,
достоверность доказательств и итог задачи. Самоадаптация не равна автоматическому
превращению любой мысли в истину или поведенческое правило.

## Что уже есть

- Пассивное дерево записей, точечный поиск и отдельная маска активного контекста.
- Кандидаты, ссылки на источники, независимая проверка перед публикацией и
  исправления с историей версий.
- `MemoryReviewDecision` на границе работы: `changed`, `unchanged`,
  `unavailable`, `forbidden`. Проверка не требует создавать запись ради отчёта.
- Наблюдения об использовании и результатах; показ записи сам по себе не
  доказывает, что она помогла или навредила.

## Предлагаемые правки

1. **Память во время работы, а не только после ответа.** При появлении нового
   ограничения, противоречия, проверенного результата или смене темы агент
   использует поиск, запись, исправление и фокус прямо внутри задачи. После
   значимого обсуждения или результата агент также спрашивает: что нового узнали, что остаётся гипотезой,
   какое предпочтение пользователь явно высказал, что противоречит уже известному
   и что будет полезно позже? Существующий `MemoryReviewDecision` использовать
   как заключительную проверку, а не единственное место работы с памятью.
   Не запускать новый скрытый цикл. Допускать `unchanged`, когда сохранять нечего;
   `unavailable` не выдавать за успешную запись. Рефлексия может создавать
   ограниченные кандидаты с точной атрибуцией, но не выдумывать подтверждение.
2. **Эволюция от наблюдения к знанию.** Различать прямое высказывание пользователя,
   вывод агента из нескольких случаев и проверенный результат работы. В памяти
   может жить помеченная гипотеза/кандидат; повторное подтверждение, коррекция
   пользователем или независимая проверка меняют её статус через существующий
   жизненный цикл. Единичное «мне понравилось» не становится правилом «всегда
   делай так». Явное устойчивое предпочтение можно предложить для записи с
   правильной областью действия; превращение в директиву требует прежних ворот.
3. **Переорганизация по смыслу.** Агент замечает дубли, противоречия, перегруженные
   ветки и пробелы, предлагает исправление, связь, разделение или объединение
   блоков. Метрики дают повод посмотреть, но не выполняют семантическую
   перестройку автоматически. Исходные записи, ссылки и история сохраняются.
4. **Повторная проверка при использовании.** Показывать дату и ссылку на
   источник, статус проверки и признаки возможного устаревания; при изменении
   исходного решения предлагать перепроверку и версионное исправление, а не
   тихую замену. Давность сама по себе не означает ложность и не должна
   автоматически менять жизненный цикл записи.
5. **Навигация без лишнего контекста.** Сначала карта подходящих веток и
   ограниченный поиск внутри выбранных блоков; широкий поиск — явное
   расширение, когда узкий не помог. Уже доступный семантический поиск
   использовать как способ найти кандидатов внутри области, не как автомат
   выбора темы, авторитета или активного фокуса.
6. **Проверка полезности и обратная связь.** На материале подтверждённых событий различать
   найдено, показано, применено и доказанно помогло/навредило. Смотреть на
   долю полезных воспоминаний, ложные срабатывания, пропуски, задержку и
   стоимость контекста. Использовать результаты для следующих решений агента о
   поиске, фокусе и проверке записей, не повышая доверие и не перестраивая дерево
   автоматически по одному счётчику.

## Масштаб, удобство для агента и стоимость

Дополнительная цель пользователя: большая, удобная для самого агента память,
которой агент управляет самостоятельно, с оптимизацией чтения, записи и
обслуживания. Оптимизировать по измеренным затратам и качеству, а не по числу
записей или объёму сжатия.

- **Маленький рабочий контекст над большой памятью.** Короткие описания веток,
  постраничная навигация, точечное чтение записей и ограниченная маска фокуса.
  Не загружать всю карту или все записи при каждом обращении. Описания помогают
  навигации, но не заменяют исходные записи и их источники.
- **Простой повседневный интерфейс.** Сделать обычные поиск, запись, исправление
  и выбор фокуса доступными без изучения всех операций обслуживания. Продвинутые
  операции открывать по необходимости; не дублировать существующие механизмы.
  Ответы инструментов должны кратко сообщать результат, идентичность записи,
  ревизию и ограничения, позволяя отдельно прочитать детали.
- **Бюджет обслуживания.** Агент сам принимает семантические решения, но
  обслуживает только затронутые ветки и работает в заданном бюджете вызовов,
  токенов и времени. Полный пересмотр дерева не нужен после каждого разговора;
  отсутствие изменений является допустимым результатом.
- **Оптимизация без скрытой смены смысла.** Проверить пакетные операции,
  индексированные точные чтения, кэширование неизменяемых ревизий и
  инкрементальное обновление описаний там, где это ещё не реализовано.
  Кэш учитывать по workspace/profile, ревизии и политике жизненного цикла;
  исправления и отзыв не должны возвращать устаревшее содержимое как текущее.
- **Масштабные проверки.** Сравнить фиксированные сценарии на деревьях разного
  размера и формы: поиск конкретного факта, исправление, продолжение обсуждения,
  смена фокуса и обслуживание. Измерять качество нахождения, p50/p95 полной
  задержки, вызовы инструментов, токены, объём хранилища и стоимость записи и
  реорганизации. Не объявлять ускорение улучшением, если потеряны источник,
  точность, изоляция или исправления.

## Примеры решений на границе разговора

- «Давай подумаем, может быть сделать X»: агент может сохранить полезную
  гипотезу как гипотезу-кандидат с источником и вернуться к ней позднее, но
  не записывает её как установленный факт.
- «Внеси X в план правок»: править файл плана; не дублировать временный TODO
  в долговременной памяти лишь потому, что появилась задача.
- «Всегда отвечай мне по-русски в этом проекте»: агент может создать запись
  о явном предпочтении с нужной областью действия; активировать как
  поведенческую инструкцию только по существующим правилам подтверждения.
- Проверенный результат работы, который пригодится вновь: предложить
  запись с конкретным источником; прежнюю версию при исправлении сохранять
  в истории.

## Критерии проверки перед реализацией

- В тестовых сценариях совместное обсуждение допускает помеченные кандидаты,
  но не создаёт неподтверждённых фактов или директив; просьба изменить план
  меняет файл плана, а не порождает его дубль в памяти. Явное устойчивое
  предпочтение может сохраняться в правильной области действия.
- Повторное подтверждение и опровержение гипотезы приводят к проверяемому
  пересмотру записи; рефлексия без нового знания допускает `unchanged`.
- Для `changed` есть наблюдаемая точная операция над кандидатом или фокусом;
  `unchanged` и `unavailable` не маскируют записей.
- Изменённый источник приводит к явной перепроверке или предложению поправки,
  без потери исходного текста и истории.
- Проверки охватывают границы workspace/profile, статус кандидата, утечку
  директив, бюджет контекста и отсутствие ложного «помогло» по факту показа.
- Перед утверждениями об улучшении качества выполнить сопоставимую оценку по
  `docs/um-mem/memory_eval_protocol.md`; до неё это гипотезы продукта, не
  измеренные результаты.

- `memory/mcp_server.py:remember`, `amend`, `recall` и операции активной маски

### Приоритет 1: честная доставка фокуса и пригодные ответы инструментов

- Живой `health` показал `integration_mode=mcp_tools_only` и
  `mcp_transport_has_no_host_lifecycle_capture`. `mcp_server.py` связывает scope
  с переменными окружения и process-session fallback; это не доказательство
  привязки к реальной пользовательской сессии и задаче. Для автоматического
  контекста нужен проверенный адаптер хоста: host-issued session/task identity,
  доставка перед следующим модельным раундом, смена задач и восстановление
  после compaction. До этого явно отличать ручное разрешение маски от доставки.
- `memory/mcp_compact.py:_compact_lease` выбрасывает trace. Живой resolve вернул
  пустые items/context без причины. Сохранить компактные поля mask ID, revision,
  resolution status, scope-validation status и бюджет, чтобы отличать отсутствие
  маски от несовпадения scope, ревизии или недоступности. Не возвращать весь лог.
- Живой recall двух записей, сохранённых с `kind=user_preference`, вернул пустой
  `kind`. Проследить перенос типа через writer/native hit/compact response и
  устранить потерю на установленном участке. До диагностики не считать причиной
  конкретный бэкенд. Сохранить минимальную атрибуцию источника в краткой карточке.

### Приоритет 2: поведение агента внутри задачи

- `memory/recall_plan.py:MEMORY_WRITE_GUIDANCE` подробно описывает обслуживание
  дерева, но недостаточно явно связывает обычную работу с поводами вспомнить,
  исправить или сменить фокус. Сделать короткие рекомендации по этим действиям;
  семантический выбор оставлять модели, без regex-триггеров и обязательной записи
  после каждого tool call. Инструкции обслуживания выдавать по необходимости.
- В этом разговоре агент читал и писал пассивную память, но не выбирал маску.
  Это наблюдение о поведении агента, не доказательство неисправности масок.
  Проверять полезность фокуса на реальном длинном исследовании со сменой подтем.
- Первая запись о видении продукта объединила прямое пожелание пользователя и
  расширенную интерпретацию агента. Разделять атрибуцию в записи: точная цитата,
  автор, вывод агента и степень подтверждения. Проверка должна работать в момент
  записи/исправления, не только перед финальным ответом.
- Требование хранить лишь проверенные устойчивые факты в проектном skill
  ограничивает сохранение гипотез и незавершённых идей. Согласовать инструкции
  хоста с моделью явно помеченных кандидатов; не обходить текущие ограничения
  самовольной записью. Текущий план реализации остаётся в файле.

### Приоритет 3: локальная навигация на большом дереве

- `api.py:block_map` загружает топологию и компилирует каталог целиком до выдачи
  ограниченной глубины. `api.py:expand_block` вызывает `list_blocks`, затем
  `edges_for` для каждого блока, хотя запрошена одна ветка. Ограниченная выдача
  пока не означает ограниченную стоимость её построения.
- Сделать точечные чтения выбранного блока, его пути, детей и соседних связей;
  добавить пагинацию широких веток и ревизионно согласованный кэш там, где это
  оправдано измерениями. Не загружать всё дерево для одного раскрытия.
- Замерять отдельно стоимость навигации, поиска, записи/проекции и упаковки
  контекста. Не обещать конкретное ускорение до замеров на разных размерах дерева.

### Сквозная проверка, которую нужно добавить при реализации

Одна длинная задача: вспомнить исходное ограничение → получить новое наблюдение
→ записать кандидат с точной атрибуцией → выбрать фокус → исправить наблюдение
→ увидеть исправление в следующем модельном раунде → сменить подтему → проверить
отсутствие утечки в параллельную задачу → пройти compaction → завершить работу.
Измерять потерянные/устаревшие факты, стоимость инструментов и контекста; отдельно
проверять инструменты-only и подключение с реальными lifecycle hooks. Успешный
unit-тест resolve сам по себе не доказывает доставку контекста в хосте.
